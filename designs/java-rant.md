Man do I hate working with Java.

And I don't mean that as a diss to the technology. The concept/design philosophy behind it is really cool. Just having to write your code once and expect it to be able to run on every environment (so long as it has a conformant JRE) is a killer feature. For other lower level languages like C and C++ or my favourite, Rust. You _have_ to build an executable for each platform/execution environment. For Linux alone, there are 2 major CPU architectures you have to account for x86_64 and ARM so that's at least 2 builds, support another lib c implementation (such as musl) and you would've 4 builds to manage. If you wanted to add more OSes/architectures then be sure to tally up all the possible combination. Whereas with Java, you just have to build a single executable .jar file and if it doesn't work for whatever reason, just point your finger at your user's JRE implementation.

Though that isn't how things would play out in the real world of course because computers are complicated. The parody "write once, debug everywhere" serves as proof to the former statement.

The text above makes a nice introduction but it doesn't convey the problems I have with this god forsaken language because of course, the user doesn't really care about what turns the machine's gears, they just want an app that works and doesn't look like an abstract artwork from a mentally ill artist. Java's developer experience or DX is that I aim to criticise in this short rant.

# The module system

Of all the languages that I've had the chance to work with in the past, none of them required me to fill out, again, how I choose to structure my code. Shouldn't the directory structure be enough for the compiler to do it for me like every other languages? Rust sure doesn't make me do it, even C with its header files that forces its users to declare public functions twice doesn't make them go through this. If it was added due to a technical limitation of the time, can't it be optional for modern Java code?

That aside, the module system was probably formulated as a way to enforce the design rules of an object oriented language. While some of its restrictions are for sure annoying, I don't think of it as anything bad, just mild annoyances I have to keep in mind when writing Java. Which brings me to another pain point.

# One public class per file limitation

This is probably another design rule of the object oriented world that I can't really get behind. If you were to look at the `vehicles` sub-module of the package `vehicles` (excellent naming scheme, I know), you'd see that for some vehicle would have a corresponding `VehicleColor` class. This is due to the mentioned restriction. Since vehicle colors can only be one of the few colors I decided to implement, passing random colors into it simply isn't an option. Sanitizing inputs isn't something I'd like to do as it indicates that your data model could be flawed so I don't really want to have to deal with that. Luckily, Java has this feature called enums, that would be the perfect solution for this problem as it makes invalid states unpresentable. Java enums aren't what I would consider real enums like they have over at Rust/Haskell land, they're more like the int-in-a-trench-coat implementation of enum in C but it'll still to for the problem I have at hand.

The `Vehicle` class will obviously need the `VehicleColor` class and it's not like it'll be useful anywhere else so the obvious/natural solution will be to put the `enum VehicleColor` declaration somewhere within the `Vehicle` class and forget about it. But it's not so simple as other classes such as `VehicleFactory` will obviously need it to construct a `Vehicle`. Letting the `Vehicle` constructor do the color randomization could work but I'd rather not have an indeterministic constructor. Which forces me to break `VehicleColor` into its own file even when no other classes could realistically make use of it.

Another casualty of this rule is in the `RoadNetworkLoader` class. Since this class reads a .graphml file and parses it into a `RoadNetwork` there's a lot of ways in which this class could fail. Since I wanted to be a good developer wanting to cover all the possible cases that it could fail and handle them properly only comes naturally. Properly signifying all the ways that your code could fail makes it more readable and above all, make it more maintainable.

The way you'd handle errors in Java is with the exception system. While I'd definitely prefer something skin to Rust's errors as values but this will do. To make an exception in Java, you'd need to create a class that inherits from the base `Exception` class. Since I wanted something more natural (to me at least). That inherited class should be an abstract class that other, more specific exception classes would inherit from. Let's say that the function could fail in 2 different ways, I would have to create this inheritance tree
```
Exception <-- RoadLoaderExcepton <+--  FileNotFoundException
                                  |
                                  +-- InvalidFormatException  
```
to properly convey that a method could fail, you'd write something like this
```java
public static RoadNetwork readFromStream(InputStream XMLStream) throws RoadLoaderException;
```
so making use of built-in exception classes such as `FileNotFoundException` is obviously out of the question as it doesn't inherit from `RoadLoaderException`. So to properly convey that a method could fail in 2 ways I would need to make at least 3 new files mostly of boilerplate code. Which obviously I am not a fan of. I got too lazy and simply guess which category the error falls into when the method inevitably fails. Maintainers (me) be damned.

# You will use an IDE and you will like it

Java is just one of those languages that assumes that you're coding with a dedicated IDE (IntelliJ, Eclipse, ...) because good luck manually typing out those imports/package declarations. This effectively means that non-IDE users are second-class citizens, which includes me, a Neovim user. I won't get into the details about why I refuse to use a dedicated IDE, which mostly boils down to having to learn another piece of software that I will only use for one specific tasks. Java offers, without a doubt, the worst tooling experience I've ever seen, and by a landslide too. With other languages, I can just install my LSP server of choice, copy a template configuration file over and maybe adjust a few things here and there and that's it. I can move on with my day. Apparently things are not so simple with Java.

For a university assignment, I had to create a directory containing multiple repos, a "we have monorepos at home" type of assignment if you will. Since I already know how to use Gradle (because of this project), I thought this would be a simple solution but the TA wouldn't allow it for some reason. Rawdogging java with a justfile as a build script was my next option and oh boy was I in for a ride.

Things never work out the way you'd want it to. That's my experience with rawdogging java summed up in a single sentence. JDTLS, for some reason, would absolutely refuse to recognise the project's structure, despite my best effort to try and lay out things in the way it'd expect. There's this issue where JDTLS won't even try to resolve local imports and assert that the current file's package name is "", which is obviously incorrect. I've gotten a habit where before each assignment day, I'd do a bit of fiddling and it would work, but for that specific moment only. This happened multiple times. Eventually, I got tired and realised that for Gradle projects specifically, it works exactly the way it should so my solution was to copy over random files until things work out and it did! Turns out, I was missing a `.classpath` file which probably serves to indicate where to look for classes as its name implies. Mind you, nowhere in JDTLS's documentation was the necessity for a `.classpath` mentioned and JDTLS doesn't even question me about whether to create this file. I had to go through countless headaches only to discover this? As infuriating as this issue may be. I can't really point my finger at anyone or even anything. The JDTLS team? They did a great job making an LSP and most of their users probably use something like Gradle anyway. Rawdoggers like me are probably a minority who they shouldn't have to bend over backwards trying to please.
